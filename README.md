# TikkunTech Ranking Lab

**Does changing how a social feed ranks posts reduce antisemitic exposure, and what does it cost ordinary conversation?**

This project answers that question in a controlled, synthetic Twitter-like network. It runs the same users, the same follow graph and the same posts twice: once under a **"before"** ranking rule and once under an **"after"** rule (your change). Then it shows the difference: what each user's timeline looked like, how many antisemitic posts were delivered, how many people saw them, and what happened to ordinary engagement and counterspeech.

The simulation runs on **[CAMEL OASIS](https://github.com/camel-ai/oasis)**, an open-source social-media simulator. The result is a single web page, `FeedBench-Algorithm-Lab.html`, that replays the runs as live networks and before/after timelines.

> **Scope.** This is a research prototype. It illustrates a ranking *mechanism* under declared assumptions. It does not predict effects on a real platform or establish a legal conclusion. All users and events are fictional, and antisemitic posts are **placeholders** until domain experts supply reviewed examples.

## 1. The idea in one picture

```
            ┌────────────────────────────┐
  users ──▶ │  OASIS simulation           │ ──▶ OASIS database (SQLite) ──▶ metrics ──▶ web page
  posts ──▶ │  (Twitter mode)             │      one file per run                        before | after
            │  feed ranked by  RULE X ────┼──▶  run with rule "before"
            │                  RULE Y ────┼──▶  run with rule "after"
            └────────────────────────────┘
                  everything else is identical: same users, graph, posts, random draws
```

1. **Users.** A population of Twitter-style users is created: names, @handles, bios, communities, a follow graph and behaviour traits. They can be generated by the project or loaded from an **OASIS profile file**.
2. **Scenario.** A fictional event (a regional bank collapse) is scheduled. A small, tightly connected group pushes antisemitic posts, other users post ordinary content, and some reply with counterspeech.
3. **Simulation.** OASIS runs the network round by round. Each round, every active user's feed is ranked by **our ranking rule**, delivered by OASIS in exactly that order, and the user reacts (like, repost, reply, post, or scroll past).
4. **Paired runs.** The same world is run once per rule. Users, graph, posts and every random draw are identical ("common random numbers"), so **any difference comes from the rule alone**.
5. **Database.** Each run is a normal OASIS SQLite database: users, posts, likes, replies, follows, and every delivered feed in the `trace` table. FeedBench adds its own `feedbench_*` tables for expert labels and simulation roles.
6. **Metrics.** Antisemitic exposure, reach, ordinary engagement, counterspeech exposure, and the reach of a legitimate Jewish community post are computed **from the database**.
7. **Web page.** The lab page shows everything side by side: a live network, timelines, charts, and a comparison of all rules with automatic feedback.

## 2. Quick start (Windows PowerShell)

### Just look at the results
Double-click **`FeedBench-Algorithm-Lab.html`** in this folder. It is a standalone page with no server or install needed. Press **▶ Play live**.

### Run the simulation yourself
OASIS needs **Python 3.10 or 3.11**. `uv` installs it without touching your system Python.

```powershell
cd feedbench
py -m pip install --user uv                        # once
py -m uv python install 3.11                       # once
py -m uv venv --python 3.11 .venv                  # once
py -m uv pip install --python .venv\Scripts\python.exe -r requirements.txt

.venv\Scripts\python.exe -m pytest tests -q        # checks (about 1 minute)
.venv\Scripts\python.exe build_lab.py --quick      # 1 seed, 2 scenarios   (~5 min)
.venv\Scripts\python.exe build_lab.py              # full: 4 scenarios x 6 rules x 3 seeds (~10-25 min)
```

`build_lab.py` runs OASIS and writes `..\FeedBench-Algorithm-Lab.html`. Everything runs offline at no cost: agents follow scripted, transparent rules. The optional LLM mode is described below.

## 4. Key concepts

**Communities.** Users belong to one of three network communities (Riverside, Midtown, Hillcrest). A community is a cluster in the follow graph, not a demographic or political identity.

**Endorsement.** A like or repost. `e[g]` = the number of *distinct* users in community `g` who endorsed a post. Replies are not endorsements.

**Ranking rules** (in `feedbench/feedbench/ranking.py` and `custom_rules.py`):

| Key | Rule | Popularity term |
|---|---|---|
| `total_endorsements` | **A · baseline** | `e0 + e1 + e2` |
| `community_capped` | **B · capped per community** | `Σ min(cap, e[g])`, cap = 2 |
| `diminishing` | D · diminishing returns | `Σ √e[g]` |
| `breadth_bonus` | E · cross-community bonus | total + 1 per extra community that endorsed |
| `bridging` | T · bridging | only endorsements from *other* communities count |
| `chronological` | N · no popularity | network + recency only |

Every rule shares the rest of the score: a bonus if you follow the author, endorsements by people you follow, your past engagement with the author, and recency. Each feed has 5 slots: 2 from people you follow, 2 recommended, and 1 random "explore" slot. **No rule ever sees the antisemitism label.** Antisemitism is measured afterwards, so any effect comes from the ranking mechanics alone.

**Scenarios** (in `feedbench/feedbench/config.py`):

| Key | Question |
|---|---|
| `coordinated` | A tight 8-user cluster inside one community endorses nearly every antisemitic post. This is what the cap is designed for. |
| `concentrated` | The same cluster, endorsing only some posts. |
| `cross_community` | The cluster spread across all communities. |
| `benign_cascade` | No antisemitic content. A Jewish community-centre post is heavily endorsed by its own community. What does the cap cost legitimate minority speech? |

**Metrics** (in `feedbench/feedbench/metrics.py`):
- *Antisemitic exposure*: delivered feed slots that held an antisemitic post.
- *Reach*: distinct users shown at least one antisemitic post.
- *Ordinary engagement*: likes, reposts and replies on non-antisemitic posts, plus new ordinary posts.
- *Counterspeech exposure*: counterspeech posts plus counter-replies shown under posts.
- *Control reach*: users shown the Jewish community-centre post, which measures the cost to legitimate minority speech.

Comparisons are **paired by seed**: seed 1 under rule A vs seed 1 under rule B, and so on. The range across seeds measures simulation variability only.

## 5. Workflows

### A. Test your own ranking rule
Add it to `feedbench/feedbench/custom_rules.py`:

```python
from .ranking import register_rule

def my_popularity(p, cfg):      # p.endorsers_by_comm = {community: distinct endorsers}
    return float(sum(min(3, e) for e in p.endorsers_by_comm.values()))

register_rule("my_rule", "M · My rule", popularity=my_popularity)
```

Then run it against the baseline and open the page:

```powershell
.venv\Scripts\python.exe build_lab.py --rules total_endorsements my_rule
```

A rule can also adjust the whole score (`adjust=`). See the examples in the file.

### B. Use OASIS's own user profiles
The sample profile files from the OASIS repository are in `feedbench/data/oasis/`:

| File | Content | Users |
|---|---|---|
| `user_data_36.json` | The OASIS quick-start profiles (fictional people written by an LLM) | 36 |
| `197_progressive.csv` | OASIS Twitter dataset **with its real follow graph** | 196 |
| `False_Business_0.csv` | OASIS Twitter dataset (anonymized users) | 111 |

```powershell
.venv\Scripts\python.exe check_oasis_profiles.py data\oasis\user_data_36.json      # 1. check the file
.venv\Scripts\python.exe build_lab.py --profiles data\oasis\user_data_36.json --quick --out ..\FeedBench-Lab-OASIS-Profiles.html   # 2. simulate
# 3. open ..\FeedBench-Lab-OASIS-Profiles.html
```

Names, handles, bios and personas come from the file, and a Twitter CSV's follow graph replaces the synthetic one. The OASIS Twitter CSVs contain **real public accounts**, so they are **pseudonymized**: names become `User N`, bios are hidden, and personas are only used to drive LLM agents, never shown.

### C. LLM agents (OpenAI), following the OASIS quick start
`run_llm.py` uses the OASIS quick-start API: `generate_twitter_agent_graph` → `oasis.make(platform=…)` → `ManualAction` / `LLMAction` → `env.step`. An OpenAI model decides every like, repost, reply and post, while our rule still orders the feed.

```powershell
$env:OPENAI_API_KEY = "sk-..."                                   # never commit keys
.venv\Scripts\python.exe run_llm.py --agents 20 --rounds 10       # prints a cost estimate only
.venv\Scripts\python.exe run_llm.py --agents 20 --rounds 10 --yes # runs
.venv\Scripts\python.exe build_lab.py --from-json results\lab.json --add-json results\lab_llm.json
```

LLM-written posts are *unlabeled* until experts review them.

### D. Plug in OASIS databases from elsewhere
```powershell
.venv\Scripts\python.exe db_to_lab.py --dir path\to\dbs --policy-from-name --labels expert_labels.csv
```

Databases are recomputed from the standard OASIS tables. Expert labels come from a CSV (`kind,id,label`), and without labels the page says so instead of showing zero exposure. See section 6.

## 6. The OASIS database is the source of truth

Each run is one SQLite file, e.g. `feedbench/runs_full/coordinated_community_capped_cap2_seed1.db`. The page is rebuilt from it.

| OASIS table | Used for |
|---|---|
| `user` | `user_id` (= agent id), `user_name` (@handle), `name`, `bio`, follower counts |
| `follow` | the follow graph |
| `post` | posts (`original_post_id IS NULL`) and reposts; `created_at` = round |
| `comment`, `like` | replies and likes |
| `trace` | `action='refresh'` rows: `info.posts` = the delivered feed in ranked order; FeedBench adds `info.slots` and `info.scores` |

FeedBench adds these tables to the same file. OASIS never reads them, so the file stays a normal OASIS database:

| Table | Content |
|---|---|
| `feedbench_run` | policy, seed, scenario, cap, full config |
| `feedbench_user` | community, simulation role (cluster member, counter-speaker), activity, persona |
| `feedbench_post_label`, `feedbench_comment_label` | expert labels: harmful / counter / news / benign |
| `feedbench_session` | who opened the app each round, who left early or left the platform |
| `feedbench_snapshot` | per-round endorsements per community and popularity under each rule |

`feedbench/tests/test_oasis_db.py` verifies that the database alone reproduces every metric, feed order and score.

## 7. Results so far (scripted agents, 3 paired seeds, cap = 2)

Change in antisemitic impressions vs the baseline:

| Scenario | B · cap | D · √ | E · breadth bonus | T · bridging | N · no popularity |
|---|---|---|---|---|---|
| Coordinated cluster | **−19%** | −16% | −12% | −33% | −20% |
| Uncoordinated cluster | **+28%** | +30% | +11% | +40% | +70% |
| Spread across communities | **+12%** | +25% | +6% | +38% | +13% |

**What this says (under these assumptions):**
- **Where the cap helps.** It reduces antisemitic exposure only when support is **concentrated and coordinated** in one community, the case it was designed for.
- **Where it backfires.** When support is weak or spread across communities, the cap **increases** exposure, because it demotes other popular posts more than the harmful ones.
- **Cost to counterspeech.** It costs counterspeech (63% kept in the coordinated case), because counter-replies travel with the posts they answer.
- **Cost to minority speech.** The benign-cascade scenario shows how much each rule costs a legitimate Jewish community post.
- **A neutral or negative result counts.** It is a valid benchmark outcome.

## 9. Assumptions, limits and safety

- **Scripted users are not people.** They follow explicit probabilities (`config.py`, `agents.py`). Numbers describe the model, not human behaviour.
- **Assigned inputs.** Communities, cluster size, cluster placement and endorsement strength are assigned inputs, not detected or measured.
- **Exposure effect.** Seeing antisemitic posts makes some users end their session (15%) or leave (3%). This is a declared assumption.
- **Seeds.** Few seeds measure simulation variability, not statistical significance or real-world effect.
- **Harmful content.** Antisemitic posts are **placeholders** (`[HARMFUL PLACEHOLDER …]`), shown redacted. Experts must replace them with reviewed examples (e.g. from an annotated dataset) and record label rationales before any real run.
- **Privacy.** Profiles from real-account datasets are pseudonymized. Run databases (`runs_*`) are not committed.
- **Thresholds.** The automatic feedback thresholds are for display only. Acceptance thresholds should be agreed with experts **before** looking at results.
